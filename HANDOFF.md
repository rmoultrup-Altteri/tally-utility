## Session 3L's five open items

1. **A premise cannot exist without an occupant, and CI-120 says it can.** `service_locations.customer_id uuid NOT NULL` (tu.sql:4443). CI-120 — "a premise / service-location entity exists independently of any active customer and persists across occupancy transitions" — is graded `partially-structurally-enforced` because "`service_locations` is a first-class entity distinct from `customers` … so the premise survives customer-closure structurally." It is a distinct table; that is not the load-bearing claim. A NOT NULL FK makes premise identity *depend* on an occupant, so a turnover has exactly two implementations and both are lossy. **Repoint** `customer_id` and the premise's history silently re-attributes — anomalies, adhoc charges, service orders, the meter and therefore the reads all join to the new occupant, and the prior occupancy is unrecoverable because nothing recorded it ended. **Insert a second `service_locations` row** and the premise bifurcates: two location rows at one address, the meter on one, consumption history split, and CI-120's "history assignments intact" broken the other way. There is no third option, because the customer↔premise relationship **has no time dimension at all**. Recommend repoint plus a four-column occupancy record (premise, customer, start, end); the reason nobody noticed is that `service_locations` *looks* like the premise entity the invariant asks for.
2. **The move-out has no date, and closing the account switches off the monitoring for the obligation the closure creates.** There is a `move_in_date` and no `move_out_date` — `move_out` occurs zero times in fifty-nine tables — and `customers` carries a five-value `status` with **no timestamp on any transition**, while `invoice_events` carries a `status_changed` event type: the bill's lifecycle is evented and the account's is a bare column. Three things sit near the move-out and none is the occupancy's end (the final read's `reading_date` is a field-visit date and absent on a discovered departure; the final bill's `period_end` is circular since proration is computed from it; `final_billed` has no timestamp). Separately and compounding: cluster 54 rule 1 makes account closure a **mandatory deposit-refund trigger**, and `compliance_statistics` (protection and exemption expiry) and `payment_health_statistics` (NSF and auto-pay health) both filter `status IN ('active','final_billed')` — so the workflow **creates the obligation at step 8 and removes the account from the only views that would notice it was missed at step 9**. Each step is correct alone, which is the shape that survives individual code review. Recommend a constraint: no account reaches `closed` while any obligation is outstanding in either direction.
3. **`rate_schedules` has two columns for the partial-period policy, the resolution function reads only one, and the one it ignores is named `override`.** `partial_period_policy` and `partial_period_policy_override` both exist, both CHECK-constrained to the same three values, both documented as the per-schedule override. `get_partial_period_policy()` is `COALESCE(rs.partial_period_policy, t.default_partial_period_policy)`; the override column is read by nothing — no function, view, or trigger — and `_raw-schema-config-inventory.md` lists both as configurable, which is how two identical knobs reach a config UI with one of them dead. The failure is silent and its symptom is a correct-looking bill. **The part that generalises:** `gap-analysis-v5.2.1.md` describes the pair as "`partial_period_policy` … with structural override via `partial_period_policy_override`" — a layered design inferred from two column names without checking that anything reads the second. Same reading error as the enforcement-status findings, in a different document.
4. **A change of obligor is a bi-temporal event modelled as a boolean, and the period it falls inside cannot be split at all.** The contrast is checkable in one pass: a rate item changing gets `rate_item_history` plus an archive; a meter changing gets `meter_endpoint_history`, deployment lineage, and CI-123's freshness guarantee; a tariff changing mid-period gets its own cluster and a documented split; a read changing gets `replaces_read_id` and a seven-state validation machine. *Who owes the bill* changing gets `UPDATE customers SET landlord_responsible = true` — no history, no effective date, no event, no prior value. CI-004 and CI-121 both name this class of data and both are unmet. Compounding: a responsibility switch is paperwork, so no read is taken, `is_service_transition` stays false, cluster 57 never fires, and the split is an **unmarked, ungoverned estimate** on two customers' bills — outside the Phase 2A estimation governance that exists to mark and count exactly that. Kyle should pick: restrict switches to cycle boundaries, or require an off-cycle read. Day-count splitting is the third option and the one that gets built by default.
5. **A move-in turn-on is filed as a reconnection.** `adhoc_charges.charge_type` has `reconnection_fee`, `disconnection_fee`, `tap_fee` and no turn-on; `service_orders.order_type` has `new_connect`, `reconnect`, `transfer`, `seasonal_turn_on` and nothing for an occupancy turn-on. So `settings.service_transition.auto_charge_turn_on` and `turn_on_fee_default_amount` — documented, defaulted tenant settings — create a charge with nowhere to go, and both landing places harm: `reconnection_fee` conflates a move-in with post-disconnection restoration, which Domain 11 regulates on timing and fee limits and which the deposit triggers read as a credit signal; `miscellaneous` makes the amount unauditable against its own configured default. An LDC doing this reports a reconnection volume several times its real one, in the direction that looks like a company disconnecting people frequently. **The schema names the act one table over** — `meter_readings.reading_purpose` carries a ten-value CHECK including `turn_on`, `turn_off`, `initial_read` and `final_read` — so the reading vocabulary distinguishes precisely what the fee and order vocabularies do not, which makes this an oversight with the naming already settled rather than a design question. **Two enum values**, batchable with 3K's `write_off` reference type and deposit-interest transaction type as one migration.
