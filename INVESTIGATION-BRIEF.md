## 4. THE ROOT-CAUSE HYPOTHESIS — the most important section

> I found this in the last thirty minutes, while assembling this document. **It has not been independently checked and it is the single thing I most want verified.**

### 4.1 The finding

**21 of the 135 invariant entries cite `schema.sql` as their `Source`.** `schema.sql` contains **zero** triggers, policies, functions, CHECK constraints, and indexes (§2.2).

**An enforcement grade made from `schema.sql` is a claim about constraints, derived from a document containing no constraints.**

```bash
cd /Users/ryanscomputer/code/gas-billing-memory/application
grep -c "^- \*\*Source:\*\*.*schema\.sql" canonical-invariants.md    # 21

# list them with their grades:
awk '/^### CI-/{e=$0} /^- \*\*Schema enforcement status:\*\*/{s=$0} /^- \*\*Source:\*\*.*schema\.sql/{print e" || "s}' canonical-invariants.md
```

The 21 entries are CI-004, 007, 012, 013, 016, 017, 019, 025, 027, 030, 031, 032, 051, 099, 116, 117, 118, 119, 126, 127, 128. **Most are graded `structurally-enforced` or `partially-structurally-enforced`** — i.e. they affirmatively assert enforcement mechanisms that their cited source cannot contain.

### 4.2 Why this is likely the root cause

**All five of the enforcement-status defects found in this project that are schema-fact errors cite `schema.sql`:**

| entry | defect | cites schema.sql? |
|---|---|---|
| CI-025 | named a column that does not exist; claimed no constraint forbids UPDATE | **yes** |
| CI-030 | same column; same missing-constraint claim | **yes** |
| CI-031 | asked for a patch adding a nonexistent column to a trigger whitelist | **yes** |
| CI-116 | read-isolation claim false absent `FORCE ROW LEVEL SECURITY` | **yes** |
| CI-118 | graded `structurally-enforced` on a UNIQUE over a **nullable** column | **yes** |

The two *other* known-bad entries, **CI-077 and CI-120, do not cite the schema at all** — they cite knowledge-base prose. That is a **second, distinct failure mode**.

```bash
# verify the two failure modes:
cd /Users/ryanscomputer/code/gas-billing-memory/application
for ci in CI-025 CI-030 CI-031 CI-116 CI-118 CI-077 CI-120; do
  echo "--- $ci ---"
  awk -v c="### $ci" '$0 ~ c{f=1} f && /^- \*\*Source:\*\*/{print substr($0,1,130); exit}' canonical-invariants.md
done
```

**Proposed taxonomy:**

- **Type A — graded from a constraint-free source.** The grader could see columns and FKs but not triggers, CHECKs, policies, or indexes, so any statement about those was guesswork or inference. **Predicted population: the 21 `schema.sql`-sourced entries.** This would explain why the errors cluster on claims about *triggers and constraints* specifically.
- **Type B — graded from prose with no schema source at all.** CI-077 (asserts a table that does not exist), CI-120.

### 4.3 What I want an investigator to test

1. **Re-grade all 21 Type-A entries against `tu.sql`.** My prediction: **a materially higher defect rate than the ~4% (5/135) currently known.** If the hypothesis is right, several of the untested 16 are also wrong.
2. **Count how many entries cite no schema source at all** and check whether their enforcement grades are supportable.
3. **Falsify it:** find entries citing `schema.sql` whose enforcement grades are nonetheless exactly right. If most of the 21 are fine, my hypothesis is weak and the defects are just individual sloppiness.

### 4.4 If confirmed, the remediation changes

The corpus has been treating these as **individual errors requiring individual corrections** — which is what I have been doing all week, one entry at a time, with a lengthy post-mortem each time. If §4.1 is right, the correct action is **a single systematic re-grade of a known 21-entry population against the authoritative file**, plus a rule that no enforcement grade may cite `schema.sql` as its only source.

`OPINION:` this would be faster, cheaper, and far more reliable than what I have been doing.

## 6. Findings that survive, and how much to trust them

Ranked by how confident I am, with the basis stated.

### 6.1 HIGH confidence — verified against `tu.sql`, and independently checked by one subagent

**(a) `meter_readings.read_type` does not exist**, in either schema file; the concept lives in three columns. → §5.3. **The D3-2 retraction rests on this.**

**(b) A voided read is freely editable during the window its correction is computed from.** The validation trigger's whitelist is guarded by:

```sql
IF OLD.billing_period_locked = true
   AND OLD.validation_status = 'locked'
   AND NOT (v_is_void_operation AND NEW.validation_status = 'void_released')
```

It tests `OLD.validation_status`. So once a read rests in `void_released`, the whitelist is bypassed on **every** subsequent update, by **any** session, needing no flag — until it is re-locked. The schema's own `validation_status` COMMENT (tu.sql:3600) says `void_released` reads are the ones *"available to correction billing runs."* The void carve-out is also **wholesale**, not scoped to the fields a void needs, and is gated on `current_setting('app.void_operation')` — **a session variable any caller can set**, with no role or `SECURITY DEFINER` check.

```bash
sed -n '244,260p;313,360p' /Users/ryanscomputer/code/tally-utility/sql/tu.sql
sed -n '3600p' /Users/ryanscomputer/code/tally-utility/sql/tu.sql
```

`OPINION:` this is the most consequential *technical* finding in the corpus, because it sits directly under CI-005/CI-006 — cancel-rebill as a pure function replaying the original-period world. A rebill cannot be a pure function of the original inputs if the inputs are writable between the void and the rebill. **Whether this is a hole or a deliberate affordance of the correction workflow is a judgement about intent that only Kyle can settle.** I did not assume the answer.

**(c) `meter_readings` has three self-referential supersession columns**, and they were designed in together — consecutive lines 641–643 of `schema.sql`. All three exist in both files. Only `replaces_reading_id`/`replaced_by_reading_id` form a bidirectional pair (which is what CI-030's "queryable in both directions" clause requires); **`replaces_read_id` has no inverse**, yet its own COMMENT, the `validation_status` COMMENT, and both trigger error messages all direct implementers to it. **The documented path cannot satisfy the invariant; the path that satisfies it is undocumented and unindexed.**
