# A-23 seal review — Fable

**Brief:** `brief.md`, md5 `0246a2ae642dfb3dbb2196ae58c24db3` (checked). **Date:** 2026-10-14.
**Probed:** live `tally` (read-only) and a clone `a23fable` (TEMPLATE tally, TEMP revoked from PUBLIC / tally_app / tally_core, `assert_core_role_invariants()` green after the revoke). Clone dropped at the end.
**Harness caveat:** the clone was driven from a `tally` (superuser) session with `SET LOCAL ROLE tally_app`. That reproduces tally_app's privileges and RLS, but `SET ROLE` itself is checked against the *session* user, so "tally_app cannot SET ROLE to the definer owner" could not be executed (`tally_app` is NOLOGIN); it is marked predicted.

Every claim is marked **executed** (I ran it) or **predicted** (read from the SQL / catalog).

## Verdict: sound with changes

The receipt design closes both gaps in principle, and I recommend it over the three alternatives. But as written the proposal would be drafted wrong in four places that a parity test would catch only if the drafter already knew to look. Those are the blocking items. None of them changes the design; all of them change what the patch must say.

## Blocking items

**B1. The receipt table is writable by `tally_app` by default.** `pg_default_acl` carries `tally=public, r: {tally_app=arwd/tally}` and `f: {tally_app=X/tally}`: every table `tally` creates in `public` hands `tally_app` INSERT/SELECT/UPDATE/DELETE, and every function hands it EXECUTE. **Executed:** I created `public.reference_version_receipts` in the clone as `tally`; `has_table_privilege('tally_app', …, 'INSERT')` and `'DELETE'` were both **true** before any GRANT. "A new table on which tally_app holds no privilege" is therefore not the default state — the patch must `REVOKE ALL ON <receipts> FROM tally_app, PUBLIC` explicitly, and the acceptance battery must assert `has_table_privilege(tally_app, receipts, INSERT|UPDATE|DELETE) = false`. A forged receipt is the whole attack; with the default ACL the seal is open on day one. (Same for the new definer functions: revoke PUBLIC/tally_app EXECUTE and grant it back deliberately.)

**B2. Column privilege must be done as table-REVOKE + column-GRANT, and `updated_at` must stay in the grant.** `tally_app` holds table-level `UPDATE` on the three headers (`relacl … tally_app=arw`); `pg_attribute.attacl` is empty — there are no column grants today. A column-level `REVOKE UPDATE (version)` alone is a no-op while the table grant stands (predicted; PostgreSQL semantics). **Executed:** after `REVOKE UPDATE ON rate_schedules FROM tally_app; GRANT UPDATE (status, updated_at, activated_at, archived_at, archive_reason) …` a raw `SET version = version + 1` raised `42501 permission denied`, and the invoker `assert_reference_version()` raised the same — which is the proof that step 2 (definer) is required, not optional. `updated_at` is load-bearing: `enforce_rate_item_dependency()` (invoker trigger, runs as tally_app) does `UPDATE public.rate_schedules s SET updated_at = now() WHERE s.id = NEW.rate_schedule_id` as the row-version mutex for dependency writes (tu.sql ~37027). Drop `updated_at` from the grant and every dependency-edge write fails. **Executed:** the touch via the column grant succeeded. The patch must carry the sanctioned column list per header (`rate_schedules`: status, updated_at, activated_at, archived_at, archive_reason; `wna_zones` / `rate_items`: status, updated_at) and a test that `has_column_privilege(tally_app, <header>, 'version', 'UPDATE')` is false and each sanctioned column is true.

**B3. The guards run as the invoker, so `tally_app` needs SELECT on the receipts.** Trigger functions here are not SECURITY DEFINER; `enforce_version_receipt`, and the three void guards, execute with the caller's privileges. **Executed:** with no grant, the prototype guard raised `permission denied for table reference_version_receipts` from inside the trigger — the version write fails for the wrong reason and the right path is broken. The proposal's "no privilege" must become "no write privilege": `GRANT SELECT` to `tally_app`, with RLS (`tenant_isolation`, FORCE) on the receipt table so a session sees only its tenant's receipts. **Executed:** with `tenant_id` on the receipt and the standard policy, a T2 session saw 1 receipt (its own) and not T1's. The alternative — making the guards SECURITY DEFINER — widens the definer surface for nothing; reject it.

**B4. A dedicated definer owner needs EXECUTE on the RLS helpers, and an explicit grant list, or the definer fails closed.** **Executed:** a `tally_definer NOLOGIN` role owning the prototype `assert_reference_version` failed with `permission denied for function get_user_tenant_id` — not from the body, but from the `tenant_isolation` policy evaluated on its UPDATE of the header (PUBLIC EXECUTE on the helpers was revoked in -17; only tally_app holds it). After `GRANT EXECUTE ON FUNCTION get_user_tenant_id(), is_platform_admin() TO tally_definer` everything below worked. The drafting must enumerate, per definer, every table/column/function it touches (for `void_invoice()` that is ~8 tables incl. `account_ledger`, `invoice_events`, `adhoc_charges`, `meter_readings`, `invoices`, `customers`), grant exactly that, and run every definer end-to-end as `tally_app` in the battery. Failing closed is safe, but a `void_invoice()` that cannot post its ledger reversal is a mirrored -20 that does not work.

## Should-fix items

**S1. Bind the version-row guard to every INSERT and every UPDATE, not only closes.** The bi-temporal guard already freezes an asserted row (`TG_ARGV[0] = ''` → nothing mutable in place) and `recorded_at` is NOT NULL on all three version tables (no drafts), so "INSERT or close" and "any write" coincide today. Write the guard as "any write" anyway: it is the predicate from the act and will not drift when a mutable column is added. Name the trigger so it sorts first (`a0_…` sorts before `a_enforce_bitemporal_assertion`), so the editor sees "no receipt" rather than a downstream constraint.

**S2. Void receipt: add a DB-stamped `completed_at`, written by `void_invoice()` on exit, and have the guards require `completed_at IS NULL`.** The GUC design clears the carve-out on return (v5.4.2-01). A bare receipt stays open for the rest of the caller's transaction for that invoice. Predicted: the residual is thin — by the time `void_invoice()` returns, every row of that invoice has already made its terminal move (reads `void_released`, charges disposed, invoice sealed by the void-terminal branch), and `enforce_reading_born_unconsumed` stops a caller inserting a fresh `locked` read under the voided bill — but "open while the act runs, closed when it ends" is the exact property the -01 fix bought, and a write-once close column costs one statement. Fence the close with a trigger admitting only `NULL → now()` once; this keeps the table append-only in the project's sense (write-once DB-stamped column, cf. CI-121).

**S3. The receipt predicate: `(xact, header_table, entity_id)`; store `version` and `tenant_id` but do not predicate on `version`.** Binding the version buys nothing once B2 holds (no other path can move it) and breaks the legitimate "two asserts in one transaction" case (5→6→7 leaves a receipt for 6 and 7; a guard checking `header.version = receipt.version` would need `max`). Bind the *table* — a `rate_items` receipt must not satisfy `rate_schedule_versions` even though uuids make a collision implausible. Executed: the prototype with this predicate refused a close and an insert with no receipt, and admitted both with one.

**S4. Keep the in-function tenant check even with a non-bypass owner, and mirror the policy (`is_platform_admin() OR tenant match`).** Executed: under FORCE RLS a cross-tenant call through the `tally_definer`-owned function saw 0 rows and raised `40001` ("modified since read") — RLS contained it, but the message lies. The explicit check turns that into the right error. `void_invoice()` already has this shape (Step 1.1); copy it. Without the platform-admin leg, platform admins cannot edit rates.

**S5. Fences keyed on `current_user <> 'tally_app'` stand aside inside definers.** `enforce_platform_admin_grant` / `enforce_tenant_admin_grant` return early for any role but `tally_app`; inside a function owned by `tally_definer` (or `tally`) they do not fire. No definer in this proposal writes `users`, so nothing opens today, but the pattern is the inverse of the reading guard's `rolsuper` fence and will bite the next definer. Invert them to key on `rolsuper` (predicted).

**S6. Header `status` moves (activate / archive) still need no token.** After B2, `tally_app` can archive a header it read stale. Predicted: the row lock serialises it against an in-flight `assert_reference_version()` (same row), and `enforce_bitemporal_assertion` refuses new versions on an archived entity, so the editor is told — but the archiver is not. Either require a receipt for a status move too, or record it as the CI-011 boundary. I would require it: an archive is an edit of the entity.

**S7. The `rule_*` helpers and `tally_core` are not paths.** Executed from the catalog: `tally_core` holds SELECT only (INSERT on `rule_audit_findings` alone); no `rule_*` helper is SECURITY DEFINER; `rule_row_seed`'s dynamic INSERT targets rule tables. The only functions that write the three version tables or the three void-path tables are `void_invoice()` (definer) and `enforce_rate_item_dependency` / `validate_calculation_snapshot` (invoker, `updated_at` row-lock touches on `rate_schedules` / `invoices` — covered by B2 and untouched by the void guard). No event triggers, no rules (`pg_rules` empty), one schema.

**S8. Receipt log hygiene.** Put the receipt tables in the CI-014 no-delete set (`no_hard_delete`, `no_truncate` triggers, no DELETE/TRUNCATE for anyone but `tally`), RLS enabled + FORCE with `tenant_isolation`, PK `(xact, header_table, entity_id, version)` for version receipts and `(xact, invoice_id)` for void receipts, `xid8` not `xid`. Growth is one row per edit and per void — negligible. A standing audit query "receipts with no version row in the same xact" is cheap and useful (abandoned edits).

## Answers

### 1. Soundness
Closes both gaps, subject to B1–B4. Paths checked:
- **Raw version bump** — closed by B2 (executed: `42501`).
- **Version row INSERT / close without the check** — executed today as `tally_app`: both succeed with no `assert_reference_version()` call (the gap, confirmed). Closed by the guard (executed: `restrict_violation` with no receipt; admitted with one).
- **Other definer / trigger functions** — see S7; none write version rows; the `updated_at` touches are not version writes.
- **`rule_*` helpers, `tally_core`** — S7; no path.
- **TRUNCATE** — `tally_app` holds no TRUNCATE (`relacl … arw`) and `no_truncate` triggers exist. Executed: `permission denied`.
- **COPY** — executed: `COPY FROM not supported with row-level security` for a non-bypass role; closed by RLS before any trigger.
- **Writable CTE** — executed: `WITH w AS (INSERT …)` hit the guard and was refused.
- **Multi-row** — FOR EACH ROW: each row needs a receipt for *its* entity; one unreceipted row aborts the statement (predicted; the single-row path was executed, the two-entity statement tripped an unrelated constraint first and landed 0 rows).
- **Void: release a locked read / un-bill a charge / `status = 'void'`** — today any caller can `SET LOCAL app.void_operation = 'true'` (predicted from the three guards; the brief states it was verified). With the receipt the guards ask for a row only `void_invoice()` can write, bound to `OLD.locked_by_invoice_id` (reads), `OLD.billed_on_invoice_id` (charges) and `OLD.id`/`NEW.id` (invoices). The GUC must be removed from every function body; the battery should assert `count(*) = 0` over `pg_proc.prosrc LIKE '%app.void_operation%'` — executed: the live DB holds it in **four** function bodies (`enforce_reading_validation_workflow`, `void_invoice`, `enforce_invoice_immutable`, `enforce_adhoc_charge_immutable`; tu.sql carries older copies of three of them at lines 250, 1224, 12642, 13832, 14139 that the patch must not resurrect). A stale copy left in one of them reopens AC-12.
- **What the seal does not close:** an application that reads the version inside its write transaction and passes it straight to `assert_reference_version()` always passes. The database cannot tell a fresh token from a stale one; "the token is the one the editor saw" remains an application contract. What becomes structural is: no version write without the bump, and two editors holding the same token cannot both commit (executed: after A's bump committed, B's `assert(…, 1)` raised `40001`).

### 2. Transaction identity
`pg_current_xact_id()` is right, with one rule: the **writer** (the definer) calls `pg_current_xact_id()`; the **guards** call `pg_current_xact_id_if_assigned()` and treat NULL as "no receipt possible".
- **Savepoints** — executed: `pg_current_xact_id()` returns the top-level id inside a savepoint (4874 both at top and inside). A receipt inserted inside a rolled-back savepoint is gone with it: executed — assert in a savepoint bumped 2→3, `ROLLBACK TO` left the header at 2, and the next close was refused for lack of a receipt. A version write in a later subtransaction sees a top-level receipt (same xid8). Consistent in both directions.
- **Read-only transactions** — executed: `pg_current_xact_id_if_assigned()` is NULL in `BEGIN READ ONLY`; `pg_current_xact_id()` *assigns* one (4876, no error). Harmless, but it is why the guard must use `_if_assigned` (no side effect, and a BEFORE INSERT/UPDATE trigger already has an xid).
- **Wraparound** — `xid8` is epoch-extended and never wraps; the permanent log needs it. Do not store `xid`/`txid`.
- **Prepared transactions** — `max_prepared_transactions = 0` (executed). If ever enabled, receipt and version writes share one xid8 through PREPARE/COMMIT; nothing else can reuse it. No issue.
- **Predicate** — S3: `(xact, header_table, entity_id)`; store `version`, do not predicate on it.

### 3. Definer owner
Yes: a dedicated `tally_definer` (NOLOGIN, no SUPERUSER/BYPASSRLS/CREATEROLE/CREATEDB/REPLICATION, member of no role, no role a member of it, no TEMP, no CREATE, no default-ACL entry) should own `assert_reference_version()` and `void_invoice()`.
- **RLS:** it must *not* bypass. `tally` bypasses because of `rolbypassrls`, not ownership; FORCE RLS binds any other role, including a table owner. Executed: the `tally_definer`-owned function was scoped to the caller's tenant by the existing `{public}` policies (cross-tenant call → 0 rows), and the policies admit it as long as B4's EXECUTE grants are in place. This is the real win: a bug in `void_invoice()` that drops a tenant predicate is contained by RLS instead of acting across every tenant.
- **Superuser-keyed fences:** today `void_invoice()` runs with `rolsuper = true`, so `stamp_log_created_at` (`account_ledger`), `enforce_invoice_first_issued`, `enforce_event_written_by_db` and the reading guard's `v_super` all stand aside for it. Under `tally_definer` they bind. Predicted: `void_invoice()`'s writes are the sanctioned ones, so they should pass — but this must be executed end-to-end in the battery (reads released, both charge dispositions, ledger, events, stamp).
- **`assert_core_role_invariants()`:** executed — still green with `tally_definer` present. Add the mirror `assert_definer_role_invariants()` with the same attribute checks plus `NOT pg_has_role('tally_app'|'tally_core', 'tally_definer', 'MEMBER')` and vice-versa, and an allow-list check of its grants (has_column_privilege on exactly `version, updated_at` of the headers; INSERT on receipts; what `void_invoice()` needs). Membership is the escape: a member could `SET ROLE tally_definer` and bump versions raw. Predicted: `tally_app` is not a member and cannot (harness caveat above). Executed: `tally_definer` has no DELETE on headers, no UPDATE on `status`, `rolbypassrls = false`.
- **Open for `void_invoice()` today?** Yes — same question, worse today: it is owned by a superuser+bypassrls role with every fence standing aside. Move it in the same patch.

### 4. Tenant check inside the definer
`get_user_tenant_id()` (definer, owned by `tally`, `search_path = ''`) reads `current_setting('app.user_id', true)` and returns `users.tenant_id` for that id; `is_platform_admin()` checks `role = 'platform_admin'` on the same row. `tally_app` sets `app.user_id` freely; the tenant is whoever that user is. Executed: a session carrying T2's user id operated T2's header through the definer and saw only T2's receipts. So the in-function check is exactly as strong as RLS — no stronger (the tenant identity rests on the app setting `app.user_id` honestly, as it does for every policy) and necessary when the owner bypasses RLS. What `tally_app` cannot do (predicted from policies and triggers): read another tenant's user ids (RLS on `users`), insert a user into another tenant (WITH CHECK = USING), or promote a user to `platform_admin` (`enforce_platform_admin_grant`, keyed on `current_user = 'tally_app'` — see S5). Platform-admin path: needed, mirror the policy (S4).

### 5. Alternatives — recommendation: the receipt design, with B1–B4 and S1–S3
- **(a) Write API (revoke INSERT/UPDATE on `*_versions`, definer functions only).** Strongest seal, but it changes the app contract the brief promises to keep ("the right path looks the same"), multiplies definer surface (3 tables × insert/close, 30+ column lists that must track every schema change), and moves the bi-temporal guards' work into function bodies. Not now; it remains the right next step if the version tables ever get a second writer.
- **(b) `xmin` test on the header.** Rejected on two executed facts: (i) inside a savepoint the header's `xmin` is the *subtransaction's* xid (4875 ≠ top 4874) — any ORM savepoint breaks the check; (ii) after B2 `tally_app` can still `UPDATE … SET updated_at = now()` (and `enforce_rate_item_dependency` does exactly that), which stamps `xmin` and takes the lock with no version check — the predicate would be "someone touched the header", not "the token was checked". It also gives the void guards nothing.
- **(c) Application contracts.** Violates the standing rule (a guard must act); leaves R14 open. Rejected.

### 6. Receipts as a permanent log
Keep them. S8 covers shape, RLS, no-delete set, `xid8`. `tally_app` may read (must, B3) under RLS; no write. Growth is trivial.

### 7. Anything else — what the patch must carry
- **Mutation tests (as `tally_app`, under `app.user_id`):** raw bump → `42501`; version INSERT / close with no receipt → `restrict_violation`; with receipt → ok; receipt in a rolled-back savepoint → refused; stale token → `40001`; cross-tenant via the definer → `40001` (or the S4 error) and **no receipt row**; forged receipt INSERT / UPDATE / DELETE → `42501` (executed in the prototype); TRUNCATE → `42501`; COPY → RLS refusal; writable CTE → refused; two-entity multi-row with one receipt → 0 rows land; `SET LOCAL app.void_operation = 'true'` then a direct `locked → void_released`, `billed → pending`, `status = 'void'` → all refused; forged void receipt → `42501`; after `void_invoice()` returns, same transaction, a read locked by *another* invoice → refused, and (with S2) a row of the *same* invoice → refused; `pg_proc.prosrc` contains no `app.void_operation`.
- **Race test (two sessions):** A `assert(…,1)` holds the row lock; B `assert(…,1)` blocks; A commits → B gets `40001`; repeat with A rolling back → B succeeds and gets 2. Also A-asserts / B-archives: B blocks on the row lock (S6).
- **Invariants in the battery:** `assert_core_role_invariants()`, the new `assert_definer_role_invariants()`, the privilege matrix of B1/B2/B3.
- **Depth and TEMP fences:** the guard's receipt lookup is a read — no `pg_trigger_depth` fence needed. The receipt INSERT is a plain-function write at depth 0 by a role `tally_app` cannot become; the S2 close is a write-once column fenced by its own trigger. The fences hold only while `tally_app`, `tally_core` **and `tally_definer`** can define no code: revoke TEMP from PUBLIC and all three after every TEMPLATE clone (executed: after the revoke `has_database_privilege` was false for tally_app and tally_core and the core invariants passed), and let `assert_definer_role_invariants()` check TEMP/CREATE the way the core one does. Strict-apply the patch with `search_path = ''` and `check_function_bodies = on` before mirroring; the definers' bodies must be schema-qualified throughout and pinned `public, pg_temp` (they read RLS tables).
- **Trigger order:** name the receipt guard to sort first (S1).
- **Not in scope but seen:** `tally_app` holds DELETE on `invoices` and `invoices` has no `no_hard_delete` trigger; `enforce_invoice_immutable` fires on DELETE and admits drafts only (predicted). Worth a line in the decision log, not this patch.
