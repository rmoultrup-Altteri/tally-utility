## Blocking

### B1. Correcting a premise's state rewrites what a past read saw (Opus B1, Codex B2; both executed)
`premise_places_as_of(…, p_recorded_at)` reads `service_locations.state` as it is now, and filters the past memberships by it. -16's state guard refuses a change only while unvoided memberships of another state exist, so an operator can void the memberships and then change the state. A read at an instant before both then answers the new state and drops the old county and city. A rebill would lose those places' levies, and nothing would raise an error.
**Fix:** record the premise's state on change, and read it as known at the instant.
- New table `service_location_state_history` (tenant, premise, normalised state, `recorded_at`). The database writes it: one row when a premise is inserted, and one each time its normalised state changes (an AFTER trigger; the app writes no row and edits none). Backfilled from every existing premise at its `created_at`.
- `premise_places_as_of` takes the state from the latest history row recorded by `p_recorded_at`. If none exists, the premise was not yet known then, and the read refuses as it does today for an unknown state.
- -16's guard stays as it is (memberships are never rewritten; a wrongly placed premise is a new premise or a reviewed repair).
- Tests: the Opus and Codex path (void, then change the state; the read before it still answers Texas and its places), a read before the premise existed, the history written only by the database, and its backfill.
[design permanent, record on change: a value a past read depends on is recorded when it changes, not reconstructed; never refuse a clerk's correction where recording it suffices. -16's own rule that memberships are never rewritten stands.]
*Why not Opus's smaller fix (refuse a state change while any membership exists, voided ones included):* a premise with no memberships still reads its state's levy, so a state change after its first bill would still rewrite the past read. Refusing every change would also turn away an operator's correction of a typed state on a premise never billed.

### B2. Closing a place can leave an open levy behind (Codex B1; Opus S2, Fable S1; all executed)
The insert check needs the place's rows to cover the levy's dates. Nothing keeps that true afterwards: -16's `enforce_place()` lists every record citing a place before allowing its close, but not tax levies. A closed place's levy keeps answering. Because a levy is keyed by code, a later place reusing that code would also be covered from its first day, with no approval.
**Fix (Fable's, checked at commit):** after a place row is closed, every levy of its kind, state and code must still be covered by that code's rows. The check runs at commit, not at the close itself: a succession is a close followed by the successor row (a code's rows never overlap, so the successor cannot come first), and a check at the close would refuse every succession. A succession in one transaction passes; a dissolution waits for the utility to close its levy. `enforce_place()` is not re-issued; the check is a deferred trigger of its own (`z_check_place_levy_coverage`, ENABLE ALWAYS). The levy's insert check now takes each of the code's rows' locks shared, under READ COMMITTED, before measuring coverage, so a levy insert and a close serialise (the membership pattern of -16).
- Tests: C0 (the trigger is deferred and always), C1 (a close with no successor, refused), C2 (close and successor in one transaction, admitted), C3 (refused again), C4 (the utility closes its levy, then the place closes). Mutations N35–N37.
[-16's rule: a place is never closed from under a record that cites it. `places` is this stream's table, so no stream boundary is crossed.]
This also answers Codex S3, a code reused for a different place: an open levy can no longer outlive its place, so a reused code inherits no levy. The header states -16's convention that a successor row of the same kind, state and code is the same place.

## Notes taken
- **The published rate's range** (Codex S4, Fable N1): the fact kind's description says the range is 0 up to but not including 100, and that it is stored as published. The four-decimal rule (K-06) is for the rates a utility enters, so the levy, not the reference. The design's 2.4 is narrowed to say so. That follows Kyle's 2026-11-05 answer 11 (a pre-go-live month only with a supervisor's approval and its legacy record). Header L6.
