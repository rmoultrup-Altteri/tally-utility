## Blocking

### B1. Two overlapping state corrections leave the history out of order (Opus B1, Fable B1; both executed with two sessions)
A history row is stamped with its transaction's start (`now()`), and the reader takes the latest stamp. If the transaction that began first commits last, its row sorts below the one it overwrote. The premise then ends in one state while every read "as known now" answers the other, permanently and with no error.
**Fix (Opus's):** the recorder refuses with a serialization failure (40001, retry) when the premise already has a row stamped after its own transaction's start. Both writers hold the premise's row lock, so the second sees the first's committed row; on retry its row sorts last. Stamps stay `now()`, so a correction and the memberships voided with it carry the same instant, and a read at any instant sees both or neither.
*Why not Fable's `clock_timestamp()` with seq order:* a correction's history row would then post-date the membership voids in its own transaction, so a read at an instant between them would see the old state without its places.
- Tests: battery M13 (a row planted later than the transaction's start; the change is refused, 40001); race R3 (two overlapping corrections: the later-committing, earlier-started one is refused) and R4 (the same, one after the other: both pass).

### S3. A levy insert that waited trusts a place row committed meanwhile (Opus note)
The insert check locks the code's rows it found, then measures coverage over all rows, including a successor committed while it waited, which it never locked. That successor could then be closed without seeing the levy. -16's rule for profiles (race R19): a row committed while a writer waited is never trusted unlocked. The check now re-reads the code's rows after locking and refuses (40001, retry) if any is new. Race R5.
