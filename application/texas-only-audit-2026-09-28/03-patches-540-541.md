# Audit 03 — patches v5.4.0-00 … v5.4.1-02 (Texas-only architecture)

## Summary
- Scope: the nine patch files below, read in full. v5.4.0-00 (auth substrate), v5.4.0-01 (roles/grants/FORCE RLS) and v5.4.0-05 (dry-run guards, reversal-chain depth, Fp confirmation columns) hold **no** jurisdiction law. Nothing to report there.
- **Biggest structural problem:** `public.jurisdictions` (v5.4.0-03) is not a jurisdiction model. It is a tenant-scoped list of WNA places with no state, no service type, no parent/county, no effective dating and only one legal attribute (`wna_applicable`, DEFAULT true "the common Texas case"). It cannot anchor per-state rules. Every other place-dependent rule in scope (weather moratorium by county, PGA pool, disconnect protection) has nowhere to hang.
- **PGA is keyed one-pool-per-tenant on purpose**, justified by "16 TAC §7.5519 is a single Texas-wide mechanism per tenant — no jurisdiction key" (v5.4.0-06:39-44). `UNIQUE(tenant_id)` on settings and `UNIQUE(tenant_id, month)` on the monthly reconciliations lock that in. A multi-state or multi-division gas utility cannot be represented.
- **program_types is data rather than a CHECK list, which is an improvement.** But it is platform-global with one `is_disconnect_protective` boolean per program for every state and every service type. Its seed descriptions are written as Texas law (CI-129 deposit waiver, CI-080 EWE ≤32°F county-level, CI-081 medical+arrangement composition). Weather moratorium is modelled as a per-customer enrollment even though it is an area-wide condition.
- `regulatory_class` is a closed binary CHECK ('regulated'/'unregulated') on two tables. It drives disconnect eligibility and the allocation order, and both of those are state law that differs by state.
- Tenant policy columns (allocation strategy, minimum refund, below-threshold/escheat action, partial-period policy) are tenant-keyed only. There is no jurisdiction floor and no way to vary them per state within one tenant.
- The gas-only `meter_pressure_class` rule (Fp = 1.0 always for `residential_base`) assumes the tariff pressure base equals the delivery pressure. That is gas-only and depends on state and tariff.
- Counts: a = 3, b = 7, c = 4 (14 findings). The 16 TAC citations that appear only in comments (tamper backbilling, medical cert) are listed at the end and not counted. They carry no structure in scope.

## Theme 1 — The place/jurisdiction model

### jurisdictions is a tenant-scoped WNA place list, not a jurisdiction
- where: sql/v5.4.0-03-rating-and-wna.sql:83-98 — table `public.jurisdictions` (UNIQUE `(tenant_id, jurisdiction_code)` :95; RLS tenant policy :109)
- rule: "a premise's jurisdiction" = one tenant-owned row carrying only `wna_applicable` and `wna_zone_id`. Header :28-32 says it holds "only what D5-2 ruled". Comment :112 notes that the A-8 tax_jurisdictions and CI-093 "Texas sub-jurisdiction" questions are still open. Source: D5-2 (Atmos Mid-Tex four-variant pattern).
- class: b
- other states: there is no `state_code`, so the state of a premise cannot be derived from its jurisdiction. There is no parent/level (state → county → city → unincorporated area), so the county-level rules the schema already cites (Texas EWE is county-level, v5.4.0-04:85) cannot be expressed, and neither can county-based winter moratoria in other states (guess: several Midwestern cold-weather rules key on NWS zones or counties). There is no `service_type`: a city can be the regulator for water but not gas. There is no effective dating, so a city that adopts or rejects a rider on a date cannot be expressed and a rebill reads today's flag (this conflicts with the CI-006 reproducibility discipline). Real places are duplicated per tenant, so two utilities serving Dallas each invent their own "Dallas" row with no shared identity.
- fix: add a platform-held place registry (no tenant_id): `places(id, state_code, place_type{state,county,city,…}, parent_place_id, name, fips/geo code)`. The tenant-held jurisdiction then becomes a mapping from place to the tenant's tariff variants, per `service_type`, with `effective_from/effective_to` and a no-overlap EXCLUDE (the meter_accuracy_thresholds shape). Per-state rules key on `places.state_code` or on the place at the right level — size: L

### wna_applicable DEFAULT true — "the common Texas case"
- where: sql/v5.4.0-03-rating-and-wna.sql:89 — column DEFAULT `jurisdictions.wna_applicable`; comment :115
- rule: WNA applies unless opted out, because most Texas franchise cities accept Atmos/CenterPoint WNA riders. Source: D5-2.
- class: c
- other states: many gas LDCs have no WNA at all, and some states use decoupling instead (guess: several states such as NY and CA prefer revenue decoupling). A non-Texas tenant's places would silently default to WNA-on. WNA is also gas/heating-only, and this flag is not tied to a service type.
- fix: no default. WNA applicability should come from the tenant's tariff per service type and place (effective-dated). At most, a per-state platform default row could supply it — size: S

### service_locations carries a single jurisdiction FK alongside the Texas franchise booleans
- where: sql/v5.4.0-03-rating-and-wna.sql:120-129 — column `service_locations.jurisdiction_id`; comment :129 ("existing inside_city_limits/franchise_city columns remain as-is")
- rule: a premise resolves to exactly one jurisdiction row. The Texas "inside city limits + franchise city" model continues in parallel, as boolean and text columns defined in tu.sql (outside this scope; noted because this patch explicitly keeps it).
- class: b
- other states: a premise sits in several overlapping jurisdictions at once: state, county, city, special district, tax jurisdiction. Comment :129 itself lists BTU, pressure, rate zone, weather station and tax jurisdiction as still-open FKs. Franchise-fee and municipal-tax models differ by state (guess: some states levy gross-receipts or utility-users taxes at county level).
- fix: set the premise's place (the lowest level) and derive the ancestors, so that rules are resolved by walking up to the state. Retire `inside_city_limits` in favour of `place_type` — size: M

## Theme 2 — Weather normalisation (WNA)

### WNA settlement mode assumed monthly (D5-1)
- where: sql/v5.4.0-03-rating-and-wna.sql:132-135 (comment), :137-160 — columns `wna_zones.wna_adjustment_floor/ceiling/wna_clamp_basis`
- rule: "Under D5-1 monthly settlement there is no annual reconciliation backstop — this clamp is the only guard." The structure has no settlement-mode attribute. Monthly bill-by-bill WNA is the Texas LDC pattern. Source: D5-1, T-4 (PGW 2022 cited as the failure example).
- class: b
- other states: some WNA riders reconcile annually or use a deferral account with a true-up. Some states cap WNA by rule rather than by tariff (guess). The clamp alone cannot express an annual reconciliation, and nothing records which regime a zone is under.
- fix: add `settlement_mode` (per_bill / annual_true_up / deferred) to wna_zones, effective-dated. The per-state limits, if any exist, belong in a platform table keyed by state + service_type — size: M

### WNA clamp bounds held per tenant tariff zone (good)
- where: sql/v5.4.0-03-rating-and-wna.sql:137-160, :167-185 — `wna_zones` clamp columns; table `wna_clamp_events`
- rule: floor/ceiling and their basis are the tenant's tariff numbers ("Tenant's choice per their tariff", :160). Clamp events snapshot the bounds.
- class: a (tenant tariff data, correctly tenant-held; the basis CHECK 'percent_of_base'/'dollars' at :143/:185 is a closed list of tariff shapes, so a third shape such as percent-of-total-bill or per-therm would need a migration — minor)
- other states: fine as long as the tariff shapes stay within those two.
- fix: none required. Optionally widen the basis list when a real tariff needs it — size: S

## Theme 3 — Charge classification driving disconnect/allocation law

### regulatory_class closed binary CHECK on rate_items and adhoc_charges
- where: sql/v5.4.0-03-rating-and-wna.sql:60-64 (CHECK `rate_items_regulatory_class_check`), :69-73 (CHECK `adhoc_charges_regulatory_class_check`); comments :67, :76
- rule: each charge is 'regulated' or 'unregulated'. This drives the rule that unregulated debt can't drive disconnect (Family 9) and the regulated-first payment allocation (CI-050). Source: D7-2, citing Minnesota PUC / CenterPoint 2024.
- class: c
- other states: the categories that matter for disconnect and allocation are statutory and more than two. Some states bar disconnection for prior-premise debt, deposits, late fees, third-party or merchandise charges, or non-residential charges on a residential account. The allocation order also varies (e.g. basic service, then non-basic, then other, a guess modelled on electric retail rules). Both "can drive disconnect" and "allocation priority" are hardcoded as behaviour of the regulated/unregulated split, not read from data per state.
- fix: have the tenant tag each charge with a `charge_category` (tariffed_service, deposit, late_fee, third_party, merchandise, …). Add a platform table `charge_category_rules(state_code, service_type, charge_category, may_drive_disconnect, allocation_priority, effective_from/to, source_note)` with Texas as the first rows — size: M

## Theme 4 — Customer programs and disconnect protection

### program_types is platform-global with one protective flag for every state and service
- where: sql/v5.4.0-04-programs-and-lifecycle.sql:72-78 — table `public.program_types` (PK code only); REVOKE :243; comment :94-95
- rule: `is_disconnect_protective` is one boolean per program code, platform-wide. Header :33-37: "if elderly_disabled turns out to be deposit-waiver-only in Texas … is a row update". A row update changes the answer for every state. Source: A-11.
- class: b
- other states: the effect of each program differs by state. A medical certificate may protect for 30 days in one state and 21 days in another, renewable n times (guess on the exact values). An elderly/disabled status may block winter disconnection in one state (guess: several cold-weather rules) and only waive deposits in Texas (CI-129). Protection can also differ by service type (electric/gas vs water). The effects are not all "protective": deposit waiver, late-fee waiver, extended notice, third-party notice. A single boolean cannot express those.
- fix: keep program_types as the platform code list. Add `program_type_effects(program_code, state_code, service_type, effect{blocks_disconnect, waives_deposit, waives_late_fee, extends_notice_days…}, parameters jsonb, effective_from/to, source_note)` with the no-overlap EXCLUDE and a lookup that raises when no row is in force. Texas rows are seeded — size: M

### program_types seed descriptions state Texas law as the program's meaning
- where: sql/v5.4.0-04-programs-and-lifecycle.sql:80-92 — INSERT seed rows; notably :81 (`medical_certificate` "16 TAC 7.45(4)(H); Texas requires composition with an active payment_arrangement (CI-081)"), :82 (`elderly_disabled` "Texas deposit waiver per CI-129"), :85 (`regulatory_moratorium` "Texas EWE per CI-080 is self-executing at/below 32F, county-level"), :86 (`payment_arrangement` D8-1/D8-3)
- rule: the rule text lives in platform-global descriptions, and the composition rule (medical cert requires an active arrangement) and the EWE trigger (≤32°F, county) are presumably implemented in app/workflow code. There is no data column for them. Sources: CI-081, CI-129, CI-080, D8-1, D8-3. The citation "16 TAC 7.45(4)(H)" may be stale if RRC recodified its quality-of-service rules into the §7.4xx series (§7.460 is cited in the brief) — a guess, worth checking.
- class: c (the rules are specified only as Texas, with no per-jurisdiction home; the workflow will hardcode them)
- other states: the need for composition with an arrangement differs by state, as do the temperature threshold for a weather moratorium (hot-weather moratoria also exist, e.g. heat thresholds in some southern and western states — guess) and its geography (county vs statewide vs NWS zone).
- fix: make the descriptions neutral. Move the composition requirement, the temperature threshold and the geography level into `program_type_effects.parameters` per state (above). The EWE threshold goes in a state-keyed moratorium rule table (next finding) — size: S (text) + M (tables)

### Weather/commission moratorium modelled as a per-customer enrollment
- where: sql/v5.4.0-04-programs-and-lifecycle.sql:85 — seed `regulatory_moratorium`; table `customer_program_enrollments` :102-132; trigger `recompute_do_not_disconnect` :207-225
- rule: a disconnect moratorium becomes protective only through a per-customer active enrollment row. Source: CI-080 (Texas EWE, self-executing, county-level).
- class: b
- other states: weather and commission-ordered moratoria are area-wide and date- or temperature-triggered (Texas EWE by county forecast; Oklahoma, Kansas and Missouri-style winter rules by date window or temperature — guess on specifics). Creating an enrollment row for every customer in an area when a condition fires is fragile and doesn't record the triggering condition. The "self-executing" nature (no customer action) is lost.
- fix: add a platform `moratorium_rules(state_code, service_type, trigger_type{temperature,date_window,order}, threshold, geo_level, effective_from/to, source_note)` and a `moratorium_events(place_id, rule_id, start, end)` instance table. The disconnect check reads these alongside the customer enrollments — size: M

### do_not_disconnect is one customer-level boolean
- where: sql/v5.4.0-04-programs-and-lifecycle.sql:207-225 — function `recompute_do_not_disconnect()`; comment on `customers.do_not_disconnect` :257-258
- rule: any active protective enrollment blocks disconnection of everything the customer has, anywhere.
- class: b
- other states: a customer with premises in two states, or with gas and water at one premise, may be protected for one service or premise and not the other (e.g. a medical certificate that covers electric/gas but not water — guess). The boolean can't vary by premise, service or state, and it depends on the global flag above.
- fix: derive protection per (customer, premise, service_type) from the enrollment plus `program_type_effects` resolved against the premise's state and the date. Keep the denormalised flag only as a cache keyed at that grain — size: M

### One active enrollment per program type — D8-3 applied to all types
- where: sql/v5.4.0-04-programs-and-lifecycle.sql:136 — UNIQUE INDEX `idx_cpe_one_active_per_type` (tenant, customer, program_type) WHERE active; seed comment :86 "Max one active per account (D8-3)"
- rule: at most one active payment arrangement per customer (and, by extension, one of every type). Source: D8-3.
- class: c
- other states: some regimes allow a commission-ordered arrangement to coexist with a utility arrangement, or a limited number of re-arrangements per year (guess, e.g. Pennsylvania-style limits on PUC payment agreements). The index is also per customer, not per account or premise, and not per service type.
- fix: move the concurrency limit (`max_active`, scope level) into `program_type_effects` per state. Enforce it with a trigger that reads that data rather than with a fixed unique index, or keep the index only for types where the limit is universally 1 — size: S/M

## Theme 5 — Purchased gas adjustment (PGA)

### PGA monitoring and reconciliation keyed one pool per tenant, justified by a Texas rule
- where: sql/v5.4.0-06-pga.sql:39-44 (header: "PGA under 16 TAC §7.5519 is a single Texas-wide mechanism per tenant — no jurisdiction key"); :75 UNIQUE `pga_monitoring_settings_tenant_id_key`; :124 UNIQUE `pga_monthly_reconciliations_tenant_month_key`
- rule: one PGA deferred balance per tenant. Source: D3D-1; cited 16 TAC §7.5519.
- class: c (a structural unique key encodes the Texas assumption)
- other states: multi-state gas utilities run a separate PGA/GCA per state and often per rate division or service area, each with its own deferred account, true-up cadence and filing (e.g. Atmos files gas-cost riders separately in each of its states; Louisiana divisions — guess on detail). Even within Texas, a utility with several city-jurisdiction rate areas may carry separate gas-cost recovery (guess). Other service types have their own cost pass-through (purchased water adjustment, electric fuel/PCA), which is not expressible here. The table is gas-named.
- fix: introduce `cost_recovery_pools(tenant_id, service_type, state_code, place/area scope, mechanism{pga,gca,pwa,fuel}, effective_from/to)`. Re-key settings to `UNIQUE(pool_id)` and reconciliations to `UNIQUE(pool_id, reconciliation_month)`. A Texas tenant gets one pool — size: M

### PGA alert thresholds 10%/20% as column DEFAULTs and job fallbacks
- where: sql/v5.4.0-06-pga.sql:69-70 — DEFAULT 10.00 / 20.00 on `pga_monitoring_settings`; comment :91 ("no RRC-prescribed number exists … when no row exists the monthly job applies these same platform defaults")
- rule: starter thresholds. D3D-1 explicitly says they are not statutory, so they are tenant data.
- class: a (tenant-tunable, correctly not law). One caveat: the "no row → platform defaults" fallback is hardcoded in the job, and if a state does prescribe a filing trigger (guess: some commissions require an interim PGA filing past a deferred-balance percentage), that trigger would need a per-state platform row that the tenant cannot loosen.
- other states: see caveat.
- fix: optional. Seed platform defaults as data (keyed by state + service_type, effective-dated) and have the job read that data instead of constants — size: S

## Theme 6 — Tenant policy values that are sometimes law

### Tenant policy columns have no jurisdiction layer (allocation, refunds, escheat, partial period)
- where: sql/v5.4.1-02-tenant-configuration-history.sql:196 — CHECK `tenant_configuration_history_key_known_check` (the 13 tenant-level keys); :197 CHECK `tenant_configuration_history_ppp_value_check`; :366-409 function `get_partial_period_policy(uuid, timestamptz)` (resolution: rate_schedule override > tenant history, with no jurisdiction step)
- rule: payment_allocation_strategy, minimum_refund_amount, below_threshold_action/donation_program_name (unclaimed small credits), overpayment_handling and default_partial_period_policy are one value per tenant (effective-dated per tenant, which is good).
- class: b
- other states: several of these are bounded by state law. Allocation order (regulated-first, CI-050, is itself a jurisdiction rule — see Theme 3). Handling of small credit balances and unclaimed refunds follows state unclaimed-property law (dormancy periods and thresholds differ by state). Some commissions prescribe customer-charge proration on partial periods (guess). A tenant operating in two states cannot hold two values, and nothing prevents a tenant value that violates the premise's state rule.
- fix: add a jurisdiction step to policy resolution: rate_schedule override > tenant value > per-state platform constraint (for validation or as a floor). Where a key can vary by state within a tenant, key the history by `(tenant_id, state_code, config_key)`. Keep the time-aware, no-live-fallback contract — size: M

### tenant_configuration_history — effective-dated tenant choices (good model)
- where: sql/v5.4.1-02-tenant-configuration-history.sql:177-201 — table `tenant_configuration_history`; :366-409 lookup
- rule: append-only, effective-dated history of tenant policy, with a lookup that takes a required as-of coordinate and returns NULL (no live fallback) before the first row.
- class: a (for tenant choices; the lookup contract matches the meter_accuracy_threshold_for model except that it returns NULL instead of raising)
- other states: n/a — this is the right shape to reuse, extended with a state key as above.
- fix: none. Consider raising instead of returning NULL, for parity with `meter_accuracy_threshold_for` — size: S

## Theme 7 — Gas-only measurement assumptions

### meter_pressure_class ('residential_base','elevated') with "Fp = 1.0 always" for residential_base
- where: sql/v5.4.0-02-meters-and-reads.sql:62-64 — CHECK `meters_meter_pressure_class_check`; comment :66-67 (engine rule CI-029). The companion confirmation columns are in sql/v5.4.0-05-pipeline-and-events.sql:178-201.
- rule: two closed pressure classes, and the engine always forces Fp = 1.0 for residential_base. Source: D3-1, CI-029.
- class: c
- other states: the pressure base in which gas volume is billed differs by state rule or tariff (commonly 14.65 psia vs 14.73 psia — hedged; Texas practice is often cited as 14.65). Whether standard residential delivery (e.g. 7" or 0.25 psig) is treated as Fp = 1.0 therefore depends on the jurisdiction and the tariff, not on a universal rule. Some tariffs define more than two pressure tiers (guess). The column is meaningless for water and electric meters but is not tied to service type.
- fix: a platform `gas_measurement_bases(state_code, pressure_base_psia, temperature_base_f, effective_from/to, source_note)`. Tenant tariff pressure tiers as data (tenant-held rows, each with a delivery pressure), not a two-value CHECK. Fp is computed from the tier and the state base, with the CI-029 override applying only where the tariff says so. Restrict the column to gas meters — size: M
