## What it is

A-3 (v5.4.2-04) made `invoice_calculation_snapshots` the record of WHICH temporal coordinate pair `(valid_at, recorded_at)` a bill was priced at, and refused only a future `recorded_at`. The A-7 reviews showed a backdated pair hid a surcharge rule and a rider's calculation type; A-7's gate now judges on now() and A-23 (1e) recorded the follow-up. This patch binds the pair to facts the database holds. Ryan ruled strict on both open calls (2026-09-08): an ordinary bill is priced at exactly `period_end`; a correction with no correction-run target row is refused.

1. **Binding** in `validate_calculation_snapshot()` (redefined, same trigger) through a new pure-read helper `calculation_snapshot_coordinate_violation(invoices, date, timestamptz, at_issuance boolean) RETURNS text` (NULL = admissible):
   - ordinary invoice (every type but correction): `valid_at = period_end`; `recorded_at ∈ [billing_runs.started_at, now()]` on a run (run must have started) or `[invoices.created_at, now()]` off-run.
   - correction: must be on a run with `run_type = 'correction'`, carry `replaces_invoice_id`, and have a `correction_run_targets` row for (run, replaced). `valid_at = get_correction_rate_date(run, replaced)` (the v5.2.1 SECURITY DEFINER resolver: historical = voided bill's period_end; current = session CURRENT_DATE at insert; custom = override). `recorded_at` in the run's window OR exactly the replaced bill's snapshot `recorded_at` (16-bi-temporality §5.1 "original world's truth").
   - The validator holds the run row and the target row FOR SHARE for the writer's transaction.
2. **`billing_runs.started_at` is the database's clock**: stamped now() on INSERT-with-value and on NULL→value; write-once afterwards; superusers exempt (migrations). `correction_rate_mode` frozen while any snapshot cites the run.
3. **`correction_run_targets` election frozen** (run, voided invoice, rate_date_mode, rate_date_override; DELETE too) while a snapshot exists for the correction invoice replacing that voided invoice on that run.
4. **Snapshotted drafts**: `invoice_type`, `replaces_invoice_id`, `billing_run_id`, `period_start`, `period_end`, `created_at` frozen while a snapshot exists ("delete + re-snapshot"); `invoices.created_at` stamped now() on INSERT (superusers exempt).
5. **Issuance re-check** in `enforce_invoice_has_snapshot()` (redefined, same deferred trigger) with `at_issuance = true`: full ordinary shape; for a correction the target must still exist and `recorded_at` must still satisfy its rule — `valid_at` is NOT re-derived (current-rules = CURRENT_DATE at insert; issuance may be a later day; the freezes are what hold it).
6. The three freeze guards refuse any isolation level but READ COMMITTED when a frozen column is actually changing (AC-29's rule). All new triggers ENABLE ALWAYS.
7. Report, never refuse: counts pre-patch snapshots that would now fail, and runs with snapshots but no `started_at`.

Deliberately NOT landed (attack these decisions): no binding for `invoice_type = 'duplicate'` beyond the ordinary shape (no lineage column — `replaces_invoice_id` is the reversal chain); no re-derivation of a correction's `valid_at` at issuance; no reimplementation of `get_correction_rate_date` (its 'current' branch is session CURRENT_DATE — the binding inherits that day boundary); nothing verifies the engine passed THIS pair to the `*_as_of` lookups (CI-003 / R-16).

## What to attack

- **Escape routes around the binding**: any way to land or issue a snapshot whose pair the run did not actually use — via invoice_type other than correction (credit_memo / consolidated / prebill / final / duplicate with a replaces_invoice_id), consolidated parents and children, a target row for a different meter, a target whose voided invoice is not void, a correction whose replaced invoice has no snapshot, superuser-only paths that tally_app can reach indirectly (functions it can EXECUTE), `void_invoice()` interplay.
- **The clock**: is stamping `started_at` / `invoices.created_at` on INSERT safe against every existing flow (billing-run phases, imports)? Any column the engine legitimately backdates? Does the superuser exemption leak (SECURITY DEFINER callers)?
- **The freezes**: is the "frozen while a snapshot exists" set complete? What else does the helper read that can move — `billing_runs.run_type`, `billing_runs.id`, `invoices.customer_id`, the replaced invoice's snapshot (immutable?), the target's `meter_id`? Can a snapshot be deleted and re-inserted under a changed election in a way the issuance re-check misses?
- **Issuance re-check semantics**: is skipping `valid_at` re-derivation for corrections defensible, or is there a route that changes the election without tripping a freeze? `at_issuance` re-checks `recorded_at` against `started_at` — any false refusal?
- **Concurrency**: the FOR SHARE handshake covers run + target. What about two snapshots racing on the same correction, a snapshot vs. `started_at` NULL→value, a snapshot vs. the replaced invoice's snapshot delete (draft original)? Deadlock shapes?
- **CURRENT_DATE / TimeZone**: the current-rules election compares a date the engine computed in its session to one the trigger computes in the same session — any legitimate flow where they differ (midnight, different TimeZone between phases)?
- **RLS / privileges**: FOR SHARE on `billing_runs` / `correction_run_targets` as `tally_app`; the helper is invoker-rights but calls a SECURITY DEFINER resolver — cross-tenant leak through `get_correction_rate_date`'s NULL/non-NULL?
- **False refusals on legitimate flows**: a regular run that computes in one transaction and inserts the draft in a later one; off-run invoices created days before pricing; a correction run for a bill issued before A-3 (no original snapshot).
- **The report**: does it mis-count, or could it ever raise?
