## 1. The spec

Same traceability as my r2/r3 reviews; the r5 changes close the two Step-2 format rules Codex found open: **V5** (any object with `strategy` requires a bounded integer `version`, `law/README.md:67` says so) and **V8** (a law kind's delegated branch is exactly the standard document, `law/README.md:89–98`). Everything else classed Step 2 is held or stated: V1–V4, V6, V7, V9, V10 (W4, with R7's limit); F1–F4, F7; T1–T6 (T7 is R2); U1–U4; P1 (class scope R10), P3; C1–C4 (R1, R8, R13, R15); L1–L4 (R11). Not Step 2: V2's kinds, F5/F6, U5, P2, P4.

**-13 migration.** `backbilling_rules` (sql/v5.4.2-13-backbilling-caps.sql:674–744) fits: `id` PK, `state_code`/`service_type` text NOT NULL, `effective_from/to`, `source_note`, `created_at`, `recorded_txid bigint`, `closed_at`, `closed_by text`; its area key `customer_class, cause` is text NOT NULL (their vocabulary FKs can stay). It must add the law columns and the nullable document columns, set `owner_types` etc. **and compute the three spans itself** before registration (R14 step 1 says "the applicability set"; it should say the spans too — the insert trigger never runs for rows already there, and A3e refuses a fill whose stored spans disagree), drop `a_enforce_backbilling_rule_history` (R14 step 3), and replace its old exclusion (13:744, no owner/system/jurisdiction dimensions) if those dimensions ever need distinct rows. Its `a_enforce_backbilling_rule_record` BEFORE INSERT trigger sorts before `rule_row_insert` and only raises, so it is harmless (see S2 for why the order matters); under the convention it becomes an `insert_check`. Adoption then fills each row once through the sanctioned path, and new rows insert normally (A4).

**-15 rewrite.** `deposit_rules` (15:465–496) keys on `customer_class, basis`, both text NOT NULL; the tariff side gets `rule_tariff_check` and the shared-key filter (R16 applies: a city's own class vocabulary must not reuse the law's column name). The template choices are right for both: applicability as sets with NULL = every one and overlap on spans; area key NOT NULL compared with `=` (R3: a per-class row or no class in the key); records cite the law row always and the tariff optionally (C2g shows the delegated-law-without-tariff case has nothing to charge); the one-time adoption; `rule_row_seed`'s "same row" = state, service, applicability sets, key, start.

## 2. Integrity

Probed as `tally_app` / `tally_core` with `SET LOCAL app.user_id` where the guard is about them (probe sets on `fable17_p2`, rolled back):
- **Privileges**: `tally_core` cannot call `rule_row_seed`, `rule_table_register`, `assert_core_role_invariants`, `assert_tenant_isolation_invariants`; cannot write law rows, tariff rows, facets, ordinals, published values or finding kinds; cannot close a law row; cannot `CREATE FUNCTION` (no CREATE on public) nor `CREATE TEMP VIEW` (no TEMP); can read `rule_tables` and run the interpreter. `tally_app` cannot run the seed or close a law row.
- **Tariff rows**: a writer's `created_by`, `recorded_txid`, `created_at`, `closed_at`, `closed_by` and a consistent `terms` are all overwritten by the stamps (T-1, T-2); a row for another tenant is refused before the policy fires because that tenant's profile is not visible (T-3); a close stamps `closed_by` from `app.user_id`, not the writer's value (T-4); changing a facet, `tenant_id`, or reopening a closed row is "never edited" (T-5..T-7); a non-object document, a duplicate key inside an array object, a system kind of another service, `effective_to <= effective_from` are refused.
- **Audit findings**: a core session of tenant 2 cannot record a finding for tenant 1 (subject not visible, F-1); `coverage_to < coverage_from`, `detail` not an object, a `pg_catalog` subject table, `rule_table` without `rule_row_id` are refused; `found_at`, `recorded_txid`, `terms_kind/version` supplied by the writer are overwritten (F-8); a law row as the rule row is allowed (by design, law has no tenant).
- **Core inputs**: a calc for another tenant's charge is refused by the policy (I-2); `tally_core` cannot UPDATE the fixture's calc table. The **owner** can, and `stamp_core_inputs` is BEFORE INSERT only, so an owner UPDATE of `inputs` leaves `inputs_fingerprint` stale (I-4). Not reachable by app or core; the area's append-only grants are the guard (Codex r4 said the same). Note N3.
- **Lookups**: `rule_law_row_as_of`/`rule_law_row_cite` as tenant 1 for tenant 2 refuse (profile not visible); NULL date, unregistered table, NULL system kind, a key with an extra column all refuse by name.
- **Interpreter vs reference**: `maxLength` counts code points (200 U+1F600 pass, 201 refused — Python `len` agrees); a fullwidth digit does not match `[A-Za-z0-9]` in either; `uniqueItems` ignores key order (jsonb equality; Python dict equality agrees); 36-digit numbers compare exactly. Two inputs disagree **before the validator sees them**: `-0` and `1E2` — jsonb normalises them to `0` and `100` on parse, so the database accepts and stores the canonical form, while `lawc` refuses an exponent at load and the reference calls `-0` non-canonical. The stored document is canonical either way; this cannot make a stored row and the reference disagree. Note N2.

### Should-fix

- **S1. The delegated-branch check compares property schemas literally, so a `$ref` to an identical definition is refused, with the wrong message.** `jsonb_set(fee, '{$defs,delegated,properties,citation}', '{"$ref": "#/$defs/citation"}')` — the fixture's own `law` branch cites through that `$ref` (zz_fee.v1.schema.json:29) — fails registration with "must admit {"governs": "delegated_to_utility", "citation": "…"}" (patch 1007–1008), although the branch admits exactly that document. Safe (a refusal), but the message tells the author the opposite of the truth, and the README (89–98) does not say the branch must be written inline. Fix: resolve each property with `public.rule_terms_resolve(NEW.json_schema, …)` before the equality (as 527 does for `version`), or say "written inline" in the message and README. Add a registration case for the `$ref` form either way.
- **S2. The template's "a writer cannot choose the document, facets or stamps" holds only while no other row-level BEFORE trigger sorts after the template's.** PostgreSQL fires BEFORE ROW triggers in name order. I registered a copy of `zz_fee_rules` carrying `zz_sneak_after BEFORE INSERT` (sets `NEW.fee_cap := 9999; NEW.terms := '{"governs": "law"}'`): registration succeeded (it checks columns, hooks and rows, never triggers, 1494–1639), and the insert stored `fee_cap 9999` and an invalid `terms` — the validated values were overwritten after `rule_row_insert` ran. Likewise a `BEFORE UPDATE` trigger added after registration rewrote `source_note` during a close that `rule_row_history` had passed (H-1). Only a table owner can do this (DDL), so no application role reaches it, and -13's and -15's own triggers are named `a_…` and sort first — but nothing records or re-checks the fact, and the whole-row text compare in the history guard (2022–2023) is exactly the kind of guarantee the project does not leave to reviewer memory. Fix: (a) `rule_table_register` refuses a table with any non-internal row-level trigger other than the ones it adds (an area's logic is its `insert_check`, `close_floor`, `compare_function`, `adoption_check`), and (b) `assert_tenant_isolation_invariants()` or a new line in the AC-32 tail asserts, for every `rule_tables` row, that its BEFORE ROW triggers are exactly `rule_row_insert` and `rule_row_history` — CI then catches a later migration. Battery: a registration refused for a pre-existing trigger; mutation: drop the refusal.

### Notes

- N1. **Adoption's "nothing else changed" compares jsonb, the close compares text.** A fill that also rewrites a non-document column's scale (`legacy_cap 50 → 50.00`) passes (A-1; `(v_new - v_doc_cols) IS DISTINCT FROM (v_old - v_doc_cols)`, 2052) where a close would refuse it (T8c). Owner-only path; align with `::text` for consistency, or leave and say so.
- N2. `-0` and `1E2` in `terms_source` are accepted (stored as `0`, `100`); `lawc` refuses both at load. Not a stored-row disagreement; a line in R7 or the README ("the database normalises `-0` and exponents before the canonical check; files may not use them") would close the question.
- N3. `stamp_core_inputs` is INSERT-only; a core-written table's append-only-ness is the area's grants (R13 says this for findings' subjects; say it for inputs tables too, or have the trigger refuse UPDATE of the inputs columns).
- N4. R14 step 1 should name the spans: `owner_span`, `system_span`, `jurisdiction_span` must be computed by the migration (`rule_applicability_span`, `rule_jurisdiction_span`) before registration, since A3e refuses a fill whose stored spans disagree with its sets.
- N5. `rule_tariff_check` requires law over the tariff's whole range; a utility cannot write an open-ended tariff while its law row has an end date and no successor is seeded yet (U3b). Correct by the stated rule ("unknown law is not permission"); -15 should know that tariffs under a closing law row are bounded or wait for the successor.
