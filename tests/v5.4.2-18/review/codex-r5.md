**Should-fix S1 — acquire the migration table lock before the anchor preflight.** The first target-table ALTER is at `patch-18-frozen-r5.sql:662`, after the preflight at `:416` and identity fingerprint at `:427`. There is no explicit earlier target-table write lock. Under READ COMMITTED, a privileged writer can commit a new, legacy-valid mismatched delegation between those two SELECTs. The preflight does not see it; the initial fingerprint does; the fill clears its anchor; the adoption check cannot compare that original anchor; and the final fingerprint intentionally masks delegation anchors (`:709`). This schedule can evade the intended B2 protection.

This is a conditional concurrency finding, not an ordinary application-role bypass: the law table is platform-held and application DML is revoked. A serialized migration/writer process excludes the schedule, which is the basis of the ready verdict. Prefer `LOCK TABLE public.backbilling_rules IN ACCESS EXCLUSIVE MODE` before the preflight/initial snapshot (after the already-registered return), so the migration itself enforces that assumption. If concurrent privileged law writes are supported during rollout, treat this item as blocking.
