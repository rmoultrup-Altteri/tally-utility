**Should-fix S1 — synchronize P11 on observed locks, not elapsed time.** `tests/v5.4.2-18/migration-18.py:307–314` starts a writer that sleeps six seconds before committing, waits two seconds in Python, then invokes `apply()`, which also copies the patch into the container (`:64–67`). Neither delay proves the writer has reached its INSERT or that the migration is waiting before the writer commits. If patch startup/copy takes long enough, the delegation can already be committed before either patch's pre-flight; P11 then passes even without the early lock. Conversely, delayed writer startup can make a correct patch win the race and fail the fixture. `writer.wait()` also does not check its return code or report its captured stderr.

Give the writer a distinctive application name, establish that it holds the target relation's RowExclusiveLock, then start the migration asynchronously and observe its ungranted AccessExclusiveLock/blocking PID before releasing the writer to commit. Bound those waits, check writer success, and include its stderr on failure. This makes P11/M107 reliable evidence of the intended schedule. It is test hardening, not a defect in the current lock statement.

**Note N1 — an already-applied rerun now takes an unnecessary exclusive lock.** Frozen patch `:404` precedes the registration fast path at `:405–407`. A reader's transaction can therefore delay a rerun before the “nothing to do” notice. With a caller-supplied lock timeout, it can fail there; without one, it waits. If the caller wraps the script in a larger transaction, the acquired lock survives the DO block's RETURN until the transaction ends, extending the read outage. Data idempotence is preserved; latency/availability of reruns changes.

An optional refinement is a registration check before the lock, then a second registration check after acquiring it, before any legacy-column read. The second check keeps concurrent first applications safe. This only avoids the new early exclusive lock on the already-registered path; the rest of the script still recreates functions, applies comments/grants and checks invariants, so it is not a promise that the whole rerun is lock-free. Probe 02 checks same-transaction reentrance and lock retention, not an independently committed concurrent rerun.

**Lock analysis.** The first migration now takes AccessExclusiveLock before any pre-flight/table fingerprint read (`:404`, `:411–435`). Under READ COMMITTED, after an existing writer finishes, subsequent queries in the DO block see its commit. Once acquired, the table lock excludes later parent-table writers through fill and drop. A normal legacy child INSERT also reads its parent in `enforce_backbilling_window_term_record()` (`sql/v5.4.2-13-backbilling-caps.sql:911–919`), and its terms must be written in its parent's transaction, so ordinary child writes are not an independent route around the lock.

The later ALTERs (`:667–696`) and `rule_table_register()` (`:699`) run in this same backend/transaction. They cannot deadlock against their own already-held table lock. Registration's registry access is ordinary SQL in the same transaction, not a second-session callback. PostgreSQL documents both self-compatibility and transaction-long retention in [Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html).

This does not promise deadlock freedom against arbitrary concurrent privileged DDL or writers acquiring other relations in reverse order: the migration subsequently touches the registry, child/vocabulary tables and comments on citing tables. Such a second transaction can form an ordinary multi-relation cycle, causing one transaction to abort. No new inevitable cycle was found in the supplied migration, battery or registration call graph. The battery runs after application in a separate completed command (`tests/ci.sh:85–89`); its transaction does not overlap migration in the normal runner. P11's writer only inserts and commits, and the parent lock waits for it rather than asking it to wait for registration.

The lock's “waited for and seen” comment is specific to a fresh READ COMMITTED view. A transaction that already established a REPEATABLE READ/SERIALIZABLE snapshot does not refresh that snapshot by obtaining a table lock. PostgreSQL explicitly calls out this qualification in [LOCK](https://www.postgresql.org/docs/16/sql-lock.html). Do not infer newly supported higher-isolation migration behavior from this change; document READ COMMITTED for rollout if callers can override the default. I have not established a higher-isolation silent-adoption reproduction in this review.
