### What the lock does under concurrency (probes c1–c6, each on its own clone)
- **c1** A writer holding an uncommitted same-anchor delegation (BEGIN; INSERT; pg_sleep(5)) when the patch starts: the migration waited (~4 s), then adopted **18** rows — the writer's row became `delegated_to_utility` with anchor NULL, its protected twin kept `test_date`. The lock makes a late row visible to the pre-flight AND to the fingerprint (count 18 before and after), so the "good" late row is adopted rather than refused. Correct.
- **c2** A reader holding ACCESS SHARE in an open transaction: the migration queued behind it (pg_locks showed `AccessShareLock:true`), finished after the reader committed. Standard.
- **c3** Two sessions applying the patch (`-1`) at once: A migrated; B waited at the LOCK, then said "nothing to do" and ran the invariants. 16/16 rows, one registration. The section-2 CREATE OR REPLACE FUNCTIONs did not collide.
- **c4** A writer arriving after the lock is taken (an insert in the old column shape): it queued (`AccessExclusiveLock:false ... RowExclusiveLock:true`), then failed with `column "qualifying_test_outcomes" ... does not exist` once the migration committed. Expected; nothing half-written (16/16).
- **c5** `SET lock_timeout = '500ms'` on the migration session with a reader open: `canceling statement due to lock timeout` at the LOCK; with `-1` the whole file rolled back — child table still there, not registered, no hook functions left behind. Clean.
- **c6** An app-like session that reads `backbilling_window_term_kinds`, then (2 s later) `backbilling_rules`, in one transaction, while the patch runs: **deadlock detected**; the migration was the victim and rolled back whole (child present, unregistered, 16 rows); the reader completed. Not new to r6 — pre-r6 the ADD COLUMN took the same ACCESS EXCLUSIVE lock at the same point relative to the DROP TABLEs (patch:667, :726-728), so any session holding ACCESS SHARE on a table 3.7 drops and then touching the rules table could deadlock it before too. Safe (atomic; re-run succeeds), so a note, not a fix.

### The cap (patch:578; battery D40c)

### Should-fix (test quality, not the patch)
- **P11 coordinates by `time.sleep(2)` / `pg_sleep(6)`** (migration-18.py:307-313). Two timing holes: (a) if the writer's `docker exec` takes more than ~2 s to reach its INSERT, the migration takes the lock first, the writer queues and later errors on the dropped columns, the migration succeeds, and P11a FAILS on a correct patch — probe c4 is exactly that outcome; (b) under M107, if sections 1–2 plus the pre-flight take longer than the writer's 6 s, the pre-flight sees the committed row and the mutation is "caught" for the wrong reason. Deterministic waits close both: before `apply`, poll `pg_locks` on `m18_j` for the writer's `RowExclusiveLock` on `backbilling_rules`; have the writer hold until it sees an ungranted `AccessExclusiveLock` request (the migration waiting) instead of sleeping, then commit. (rules/web/testing: avoid timeout-based assertions.)

### Notes (nothing to fix)
- Lock-wait behaviour: the LOCK waits without bound and, once queued, blocks every new reader of the table behind it — the same hazard the ALTERs carried, moved ~20 lines earlier. The apply recipe (brief, ci.sh) could state `SET lock_timeout` for a live database; c5 shows the failure is clean.
- Locking the three tables 3.7 drops in the same statement would turn c6's deadlock into a wait, but on an already-migrated database they do not exist and the LOCK would break the idempotent path; it would have to come after the registration check. Not worth it for a safe, re-runnable failure.
