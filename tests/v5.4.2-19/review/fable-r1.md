## Verdict: **not yet** — two blocking items, each a small fix.

### Blocking

**B1. CI-055: a duplicate posting slips through the processor-transaction index as a "refund" or a "replacement"** — `patch-19-frozen-r1.sql:508-510`.
The partial index excludes any row with `refunds_payment_id` or `nsf_original_payment_id` set, and nothing ties either label to the act. Reproduction as `tally_app`: after P-2 (`+20 ach, paymentus_webhook, TXN-1`) posts, `INSERT … amount 20, payment_method 'ach', provider_transaction_id 'TXN-1', refunds_payment_id = P-2` → **ACCEPTED** (PX1); the same with `nsf_original_payment_id = P-2` → **ACCEPTED** (PX2). Two positive ACH postings of one processor transaction, which the header says cannot happen. Worse, `nsf_original_payment_id` is not a reversal row at all: its own comment (`sql/tu.sql:3909`) says "for replacement payments: points at the original bounced payment this one replaces" — a replacement payment is a fresh, positive posting with its own transaction id, and the patch exempts it from the once-only rule entirely (a webhook delivered twice for a replacement payment posts twice). Standing rule: guard the act, not the label. Fix: drop `nsf_original_payment_id` from the exclusion; keep `refunds_payment_id IS NULL` only together with a CHECK that a row citing `refunds_payment_id` has `amount < 0` (and/or `payment_method = 'refund'`), or simply index `WHERE provider_transaction_id IS NOT NULL AND amount > 0`. Add the negative case (positive duplicate labelled a refund) to the battery; P6b currently proves only the negative-amount refund passes.

**B2. CI-118: the file-once key is mutable on a live job** — `patch-19-frozen-r1.sql:814-816`.
`is_dry_run`, `source_file_hash`, `source_filename`, `import_type` are freely editable on a job in any status; there is no freeze trigger on `import_jobs` (only `set_updated_at`, `populate_import_job_idempotency_key`, `no_hard_delete`). Reproduction as `tally_app`: commit job for `h-feb` → `status = 'complete'`; a second commit job for `h-feb` → refused (JX5, correct); `UPDATE import_jobs SET is_dry_run = true` on the completed job → ACCEPTED (JX2/JX6); the second commit job now → **ACCEPTED**, and `count(*) … status NOT IN (failed, cancelled)` = 2 commit jobs of one file. Rewriting `source_file_hash` on a live job is likewise accepted (JX3), which releases the file. A check narrower than its claim. Fix: a BEFORE UPDATE trigger on `import_jobs` freezing `tenant_id, import_type, source_type, source_filename, source_file_hash, is_dry_run, idempotency_key` (write-once); battery cases for the flip and the hash rewrite.

### Should-fix (in priority order)

**S1. Block 3 freezes lock pointers only while `validation_status = 'locked'`; a void-released read's provenance is fully rewritable** — `:343`. After the void release (R6), as `tally_app`: `voided_from_invoice_id` → another bill (RV1) ACCEPTED; `locked_by_invoice_id` set with no lock (RV2) ACCEPTED; `locked_by_billing_run_id` moved (RV3), `locked_at` rewritten (RV4), `voided_from_invoice_id` cleared (RV5) all ACCEPTED; and the transition `void_released → released_to_billing` may clear `voided_from_invoice_id`, the run and `locked_at` in the same write (RV6 ACCEPTED, row left with no history of the bill it came from). The header calls the void-released read "the evidence the correction run rebills from"; the evidence of which bill released it is not protected. Fix: freeze `voided_from_invoice_id`, `locked_by_billing_run_id`, `locked_at` whenever `OLD.billing_period_locked` (with the re-lock carve-out: a move to `locked` may set the run, invoice and `locked_at`); `locked_by_invoice_id` may be set only on the move to `locked`. Battery: add the RV cases.

**S2. Block 2 trusts an app-written flag; the "consumed by a billing run" fact is caller-settable** — `:313`. Standing rule 4. `INSERT … billing_period_locked = true` on a `pending_review` read (no run, no lock) → the value edit is refused "consumed by a billing run (validation_status pending_review…)" (RF1) and the flag can never be cleared (RF2): a read frozen forever by a typo, with a message that states a falsehood. Conversely a read inserted directly as `void_released` with the flag false (RF5) is accepted and not frozen. Fix: refuse `billing_period_locked = true` on INSERT, and on UPDATE allow it only together with the move to `locked` (the DB-verified transition); refuse a read born `locked`/`void_released` (today a non-estimated read born `approved`/`locked` fails for the wrong reason, see N6). Then the flag is a DB-written fact and Block 2 can trust it.

**S3. CI-096 hash is write-once in every status while `pdf_url` is free on a draft** — `:785` vs `sql/tu.sql:14390-14391` (`enforce_invoice_immutable` returns early for draft/held). On a draft with an image: change `pdf_url` alone → ACCEPTED, hash now fingerprints the wrong object (IX1); change `pdf_url` with its new hash → REFUSED (IX2); clear both → REFUSED (IX3). The guard defeats its own purpose on the one status where re-rendering is normal. Fix: freeze `pdf_sha256` under the same condition as `pdf_url` (`is_invoice_issued(OLD.status)`), or make the draft's URL write-once too — pick one, both columns the same.

**S4. CI-019 helper: the "recorded by" coordinate is app-written** — `:883`. `account_ledger.created_at` has no DB stamp (triggers: `dry_run_no_ledger`, `compute_ledger_running_balance` only). As `tally_app`: INSERT a ledger row with `created_at = '2000-01-01'` → ACCEPTED (BX1), and `account_balance_as_of(c, 2026-01-31, recorded 2000-06-01)` returns 100 — a row written in 2026 is "recorded" in 2000. (`tally_app` has no UPDATE on the ledger, so only the INSERT path is open.) The helper is sold as the order-independent, correct reading; its second coordinate must be the database's. Fix: stamp `created_at` in `compute_ledger_running_balance` (or a `stamp_log_created_at`-style trigger; superuser keeps). Same pattern exists for `anomalies.created_at` (write-once by the trigger but caller-set at insert) — lower stakes.

**S5. Block 2 omits `days_in_period`** — `:314-335`. `previous_reading_date` is frozen but `days_in_period` (filled by the same trigger from it, and the input to tier proration — whose default this patch flips to true) is not: on a locked read `SET days_in_period = 99` → ACCEPTED (RD1). Also editable on a locked read: `raw_read_value` (RD2, the evidence behind `reading_value`), `reading_timestamp` (RD3), `estimation_reason` (RD4). Add `days_in_period` and `raw_read_value` at least.

**S6. A superseded or inactive payment method can be made default again** — `:617-622`. The AFTER trigger clears `is_default` on the predecessor; nothing stops `UPDATE … SET is_default = true` on it afterwards (MX1 ACCEPTED, row inactive and default). Refuse `is_default` on a row that is inactive or has a successor. Minor siblings: a successor may be inserted already `is_active = false` (MX2), `noc_received_at` ten years in the future is accepted (MX5b), and a `customer_update` supersede may change `method_type` ach → credit_card (MX4b) — say whether a supersession is same-account-type by definition.

**S7. Anomaly "subject" write-once covers only `entity_type`/`entity_id`** — `:720-729`. `customer_id`, `meter_id`, `location_id` (NX1), `detected_at` (NX2 — a second first-detection column the trigger ignores), `severity`, `detection_method` (NX3) all rewritable. Freeze the subject FKs and `detected_at`; or state that `detected_at` is the mutable alias of `last_detected_at`.

### Notes

- N1. The GUC carve-out: as `tally_app`, `SET LOCAL app.void_operation = 'true'` then void_invoice()'s exact write releases a locked read while the invoice stays `draft`/issued (RG1 ACCEPTED). What a caller can do now is exactly one thing — release reads from a bill without voiding it, then re-lock them under another run. Narrower than before (no value edits, no pointer games), still AC-12's accident fence. A fix that closes it fully: `void_invoice()` is SECURITY DEFINER — key the carve-out on `pg_trigger_depth()`/a function-private marker rather than a session GUC. Out of scope; record it.
- N2. Re-lock with no invoice pointer: `released_to_billing → locked` with `locked_by_billing_run_id` only (RV7) is accepted; a locked read with no bill. Pre-existing (the lock requires the run only).
- N3. Dependencies on an archived schedule are accepted (QX5b): the header bump passes the lifecycle guard because status is unchanged. R4 says `rate_item_dependencies` is not effective-dated; say whether an archived schedule's graph is frozen (one line in the trigger).
- N4. Lock order for the header mutex: a writer touching two schedules' dependencies in one transaction must take the headers in a stated order (by `rate_schedules.id`); otherwise two such writers deadlock (detected, one fails). State it in the function comment.
- N5. `trg_enforce_reading_validation_workflow` and `trg_populate_reading_calculations` are `ENABLE` (origin), not `ENABLE ALWAYS`, unlike every guard this patch adds. Pre-existing; a logical replica would not enforce Block 2.
- N6. Pre-existing (v5.4.2-05, not this patch): a non-estimated read inserted directly as `approved` (or `locked`) fails with `meters_last_validated_actual_reading_id_fkey` (RF6) — the exception gate points the meter at `NEW.id` before the row exists. An estimated read born `approved` is accepted (RF7). Not this patch's, but it is why RF3/RF4 "refuse" for the wrong reason.
- N7. Battery Q3d catches `WHEN OTHERS`, so it passes on any error, not only the bitemporal guard's; pin the SQLSTATE. L4b tests the owner's DELETE on escheatment only; owner DELETE on `ai_audit_log` is also refused (LX5, by `append_only` — `no_hard_delete` fires second). `tally_core` has no INSERT on the logs (LX4), consistent with its read-only role.
- N8. `stamp_log_created_at` superuser exemption: `tally` is `rolsuper = t`, so the battery's L1 (as `tally_app`) is the only path exercised; a history load as `tally` keeps its value, as documented.
- N9. Hash-only CI-096 and the import hash (CI-118) are caller-computed; the DB cannot verify either. Known; the contracts (R9) should say the core computes both from the bytes it stored.
- N10. The payment effective-date pair: `posted → voided` must keep its effective date (PX6 refused) — correct, a payment that took effect and was voided still has the date it took effect. Pending → reversed with code, date and method in one write passes (PX3). `check` → nsf without a code passes only for non-ACH (PX7 refused was an ACH row; by design).
- N11. `battery-11` fixture change (dedup keys added) and `ci.sh` (PENDING entry, battery 19, race `ci_r19`) are consistent with the patch.
