## Blocking

**B1. Under REPEATABLE READ the void strands an attach it waited for.** (executed) Session A, READ COMMITTED: `UPDATE adhoc_charges SET status='billed', billed_on_invoice_id=H1, billed_at=now()` (FOR SHARE on H1 via the attach guard), holds. Session B, `BEGIN ISOLATION LEVEL REPEATABLE READ`, same tenant: `void_invoice(H1, …, 'wrong_rate')`. B blocks on H1's FOR UPDATE until A commits, then completes: `charges_auto_reverted: 0`. After both commit: **H1 = void, A1 = billed on H1**, `voided_from_invoice_id` NULL. The charge can never leave `billed` (the charge guard admits that only through a void of H1, which is "not voidable: void"). Cause: B's `UPDATE adhoc_charges WHERE billed_on_invoice_id = H1` scans B's transaction snapshot, taken before A committed, so A's row version is invisible; the FOR SHARE wait buys ordering but not visibility. The same applies to the reads UPDATE. RC4 holds only because the race script runs B under READ COMMITTED. The attach side is fine under RR (FOR SHARE on a row updated after the snapshot raises 40001, fail-closed); only the void side is open. **Fix** (one clause in void_invoice, before the FOR UPDATE): `IF current_setting('transaction_isolation') <> 'read committed' THEN RAISE EXCEPTION … ERRCODE 'invalid_transaction_state'` — a void needs the statement-fresh snapshots its lock order assumes; state it in the header's lock-order paragraph and add RC4b to seal-20.sh (B under RR, expect the refusal, charge stays live on a live bill). SERIALIZABLE would also detect this, but nothing pins the application to it; refusing is the guard that acts.

**S3. The attach guard admits an invoice the caller cannot see, so a voided bill of *another* tenant takes new charges.** (executed) T2's user voids H9; T1's user, as tally_app, `UPDATE adhoc_charges SET status='billed', billed_on_invoice_id=H9 … WHERE charge_number='R20-A4'`: **admitted** — RLS hides H9 from the guard (`v_status` NULL), the FK (table-owner, bypass) passes. The pre-patch hole is the cross-tenant pointer itself (no composite FK, no tenant check on `billed_on_invoice_id` / `locked_by_invoice_id`); the patch's guard documents choosing to leave it ("left to the foreign key"), and so its claim "a voided bill takes no new reads or charges" is narrower than its check. One line closes both: in `enforce_attach_to_live_invoice`, `IF NOT FOUND THEN RAISE … 'names an invoice this caller cannot see'` (P0002). A caller with no user sees nothing and is refused — fail-closed is right here; a platform admin and a superuser see everything. Add a battery case (another tenant's live bill, another tenant's void bill, both refused) and extend `assert_tenant_isolation_invariants` if it has a shape for "FK to a tenant-scoped table without a tenant check".

**S4. "The two cannot deadlock" (header, lock order) is false when the attaching transaction has already locked an attached child.** (executed) H5 held, charge X billed on it, Y pending. A: `UPDATE adhoc_charges SET updated_at=now() WHERE id=X` (an annotation on an attached charge; row lock on X), sleep, then attach Y to H5 (FOR SHARE H5). B: `void_invoice(H5)` — FOR UPDATE H5, then its UPDATE of X waits on A. A's FOR SHARE then waits on B: **`deadlock detected`** in A; B's void completed (X disposed, `charges_auto_reverted: 1`); Y stayed pending on no bill. Nothing stranded, the loser is the attach, the retry is clean — but the claim is wrong and a billing run that touches a bill's children before attaching to it will hit 40P01 under a concurrent void. Either restate the paragraph ("an attach that first writes an already-attached child of the bill can deadlock with its void; the attach is the victim; nothing is stranded") and add it to seal-20.sh as a documented outcome, or have the attach guard take the invoice lock *before* the child is locked — not possible from a BEFORE UPDATE trigger (the child is locked before the trigger fires), so restating is the honest fix. For the record: attach-then-edit-the-same-held-bill (FOR SHARE then UPDATE of H2 while a void waits FOR UPDATE) did **not** deadlock (executed: void waited, then disposed the charge), and two attaches to one bill in one transaction did not either.

A re-parent (`SET rate_schedule_id = X` on Y's row, with a receipt for X) would be admitted by this guard.
